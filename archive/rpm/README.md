## hardlinks-ghosts-v4.rpm

An RPM v4 package with an uncompressed payload, built from the same spec as
[hardlinks-ghosts-v6.rpm](#hardlinks-ghosts-v6rpm) - the file tree and the
method used to generate both files are described there.

Its payload is a plain cpio archive (magic `070701`), whose entries contain file
names, sizes, and other metadata, so it can be parsed on its own (without having
to examine the RPM header). In contrast, in the
[hardlinks-ghosts-v6.rpm](#hardlinks-ghosts-v6rpm) sample, all file metadata is
stored only in the RPM header and the payload entries contain only file indexes
and file contents.

> [!NOTE]
> RPM itself uses hardly anything from the cpio entries: it only parses the file
> name and size
> ([`lib/cpio.cc:398-424`](https://github.com/rpm-software-management/rpm/blob/ec9ea8c43808c346da4b6cb454cdc58aef8e506a/lib/cpio.cc#L398-L424)),
> looks the name up in the header, and from then on handles the entry just like
> in a v6 package - the size of the entry's data and all other metadata come
> from the header (see `iterReadArchiveNext()` in
> [`lib/rpmfi.cc:2180-2242`](https://github.com/rpm-software-management/rpm/blob/ec9ea8c43808c346da4b6cb454cdc58aef8e506a/lib/rpmfi.cc#L2180-L2242)).
> The size in the entry is only used to skip an entry for a `%ghost` file, which
> RPM before 4.11 sometimes wrote
> ([`lib/rpmfi.cc:2217-2219`](https://github.com/rpm-software-management/rpm/blob/ec9ea8c43808c346da4b6cb454cdc58aef8e506a/lib/rpmfi.cc#L2217-L2219)).

Source: own work

## hardlinks-ghosts-v6.rpm

An RPM v6 package with an uncompressed payload, whose file tree mixes hard links
and `%ghost` files with other kinds of files.

v6 packages always store file sizes in the 64-bit `RPMTAG_LONGFILESIZES` tag,
and whenever that tag is present, RPM writes the payload as a "stripped" cpio
archive: its entries (magic `07070X`) contain only the index of the file in the
RPM header - no file name or size. Only the trailer is a plain `070701` entry.
So a parser has to map each entry to the file in the header and derive the size
of the entry's data from the header, following the rules of RPM's archive
reader, `iterReadArchiveNext()` in
[`lib/rpmfi.cc:2180-2242`](https://github.com/rpm-software-management/rpm/blob/ec9ea8c43808c346da4b6cb454cdc58aef8e506a/lib/rpmfi.cc#L2180-L2242).
The file tree covers the cases where this isn't straightforward (see the file
indexes in the table below):

* Only one member of a hard link set (files 1 and 3) carries the data: the one
  with the highest index, which is also the last one in the archive. The other
  members have entries without data, although the `RPMTAG_LONGFILESIZES` header
  tag lists the full size for each of them.
* `%ghost` files (5 and 6) have no archive entry, even if they have a non-zero
  size in the header.
* A `%ghost` file is never part of a hard link set, even if it has the same
  inode as its members (file 5). So although its index is higher than theirs,
  the data is still carried by file 3.
* Hard links to symlinks (files 7 and 8) have the same inode in the header, but
  only regular files form hard link sets, so each carries its own target.
* The archive order differs from the header order: RPM first writes the files
  that aren't in a hard link set, then the members of each set, so the order is
  0, 2, 4, 7, 8, 1, 3. The file index therefore can't be derived from the
  entry's position.

[hardlinks-ghosts-v4.rpm](#hardlinks-ghosts-v4rpm) contains the same file tree
in a plain cpio archive, so it can serve as a reference for what a parser should
read from this package.

Both packages were generated by [`hardlinks-ghosts.py`](./hardlinks-ghosts.py),
which builds them from the same spec using `rpmbuild` (RPM 6.0+ must be
installed) and checks that their file trees are identical (see the script's
docstring for details):

because it ships RPM 6.1.0. Identical packages were reproduced in the Debian 14
